주요 구현 사례

기능문제해결결과
실시간 배틀런같은 티어 상대와 달리며 WebSocket으로 주행 거리를 1초마다 주고받습니다. 15초 안에 상대를 찾지 못하면 고스트와 달립니다.매칭 요청이 겹치면 같은 사람이 두 대결에 배정되거나, 대기를 취소한 사람과 짝이 될 수 있었습니다.대기 상태 확인과 상대 배정을 Redis Lua 스크립트 하나로 처리해, 두 단계 사이에 다른 요청이 끼어들지 않게 했습니다.20명이 동시에 대기해도 짝을 만들 수 있고, 여러 요청이 같은 상대를 골라도 한 번만 배정되는 것을 시험으로 확인했습니다.
크루런크루원이 대기실에서 준비하고 함께 출발해, 달리는 동안 실시간 순위를 확인합니다.주기적으로 상태를 조회하면 크루원 수만큼 요청이 늘고, 저장 전에 신호를 보내면 앱이 이전 상태를 읽을 수 있었습니다.저장이 끝난 뒤 변경 항목과 번호를 보내 해당 화면만 다시 조회하게 했습니다. 연결이 끊겼을 때의 주기 조회는 결과 화면에만 남겼습니다.에뮬레이터 2대와 계정 3개로 목록, 대기실, 자동 출발, 중간 참여, 결과를 확인하는 자동 시험 8개를 통과했습니다.
셀카 아바타 생성AI가 셀카로 아바타 얼굴을 만들고, 앱은 작업 상태를 확인해 완성된 얼굴을 가져옵니다.실기기 시험에서 약 300초에 실패로 표시됐지만, 이미지는 345초에 저장됐습니다. 같은 사진으로 다시 요청해도 이전 실패 작업이 돌아왔습니다.Node 중계 서버의 내부 호출이 기본 대기 시간인 300초에 끊겼습니다. 호출 방식을 바꿔 15분 생성 제한을 따르게 하고, 늦게 저장된 결과는 다시 가져오도록 했습니다. 실패가 확정된 뒤 다시 요청하면 새 작업을 만들게 했습니다.기본 대기 제한을 200ms로 줄인 시험에서 200ms를 넘겨 도착한 응답도 처리했습니다. 늦게 저장된 결과를 가져오는 동작도 시험으로 확인했습니다.
디자인 시스템앱 전반의 화면 일관성을 유지하기 위해 Material Design 3 기반 디자인 시스템을 구축했습니다.여러 화면을 병행 개발하면서 색상, 모서리 반경, 서체, 버튼과 칩 스타일이 화면마다 달라질 수 있었습니다.Material Design 3(RunkkTheme)의 색상, 서체, 도형 토큰을 정의하고, 이에 맞춰 버튼, 칩, 배너, 지표 타일 등 공통 컴포넌트를 설계해 화면에 적용했습니다.전 화면의 UI 일관성과 재사용성을 확보했고, 컴포넌트 동작, 접근성 테스트와 스크린샷 테스트로 일관성을 검증했습니다.
기록 대결내 최고 기록이나 코치 기록을 상대로 달립니다. 앱은 출발할 때 받은 시간별 거리표로 상대 위치를 계산합니다.앱은 화면에 표시할 위치를, 서버는 승패 판정에 쓸 위치를 따로 계산합니다. 두 계산이 어긋나면 화면과 최종 판정이 달라질 수 있었습니다.입력과 기대 결과를 한 파일에 담아 앱과 서버의 시험이 같은 기준을 쓰게 했습니다.앱이나 서버의 계산 결과가 기대값과 다르면 시험이 실패해 차이를 발견할 수 있게 했습니다.
워치 앱워치로 혼자 달릴 수 있고, 폰으로 달릴 때는 워치에서 거리 차이와 추월 알림, 근접 진동을 확인합니다. 폰과 워치는 Wearable Data Layer로 연결합니다.근접 알림을 끄는 신호를 놓치면 워치 진동이 멈추지 않을 수 있었습니다.폰은 근접 상태가 이어지는 동안 2초마다 신호를 보내고, 워치는 마지막 신호를 받은 뒤 3초가 지나면 진동을 멈추게 했습니다.2초마다 신호가 오면 진동이 이어지고, 새 신호 없이 3초가 지나면 멈추는 것을 워치 시험으로 확인했습니다.

새로고침 뒤 복귀새로고침하면 진행 중인 게임으로 돌아갑니다.새 연결이 열린 뒤 이전 연결의 종료가 도착하면, 복귀한 플레이어가 다시 끊김으로 처리됐습니다.같은 플레이어의 연결이 남아 있으면 이전 연결의 종료를 무시하고, 게임이 끝난 경우에는 이유와 함께 로비로 안내했습니다.새로고침 뒤 원래 자리로 돌아오는 흐름을 브라우저에서 재현해 통합 시험으로 남겼습니다.

주요 구현 사례

기능문제해결결과
DB 연결 관리여러 Pod가 PostgreSQL 연결을 재사용합니다.Pod가 늘어날 때 각 Pod가 유지하는 연결 풀도 늘어 PostgreSQL의 최대 연결 수에 도달하는 것을 로그에서 확인했습니다.Pod 수와 DB 연결 수를 분리하기 위해 PgBouncer를 적용했습니다. 트랜잭션이 끝난 DB 연결은 다른 요청이 재사용하도록 했습니다.DB를 증설하지 않고 Pod를 늘릴 수 있게 했습니다.
실시간 차트Upbit 시세로 캔들 차트와 보조지표를 그리는 기능입니다.최신 봉이 있어도 중간 36일치 데이터가 비어 있는 것을 놓쳤습니다. 큰 거래량은 소수점 뒷자리가 잘려 Upbit 원본과 달랐습니다.봉 사이 간격을 검사하고 매일 일부 마켓의 캔들을 Upbit 원본과 대조하도록 했습니다. 거래량은 Decimal로 읽고 DB와 같은 소수 자릿수로 맞춰 비교했습니다.36일 공백을 감지하는지 시험했고, PostgreSQL에 저장된 거래량이 원본과 일치하는지 확인했습니다.
자동매매와 캔들 동기화Upbit 캔들을 모아 전략을 평가하고, 조건에 맞으면 모의 주문을 냅니다.최근 24시간의 확정 손실이 한도에 닿아 전략을 끌 때, 예약금은 풀렸는데 중단 상태 저장에 실패하면 전략이 계속 실행될 수 있었습니다.킬스위치의 청산 처리, 예약금 해제, 전략 중단 상태 저장을 한 트랜잭션으로 묶었습니다.킬스위치가 발동하면 전략이 중단되고 예약금이 풀리는 것을 시험으로 확인했습니다.
현물 주문과 체결시장가와 지정가로 암호화폐를 모의 거래하는 기능입니다.주문이 동시에 들어와도 같은 잔고를 중복으로 쓰지 않고, 체결 내역과 잔고를 일치시켜야 했습니다.DB에서 잔고를 잠근 뒤 주문에 필요한 원화나 코인 수량을 예약했습니다. 체결 내역과 잔고는 한 트랜잭션에서 갱신했습니다.주문을 취소하면 예약이 풀리고, 체결되면 잔고에 반영되는 것을 시험으로 확인했습니다.
백테스트여러 지표를 조합한 매매 전략을 과거 시세에 적용하는 기능입니다.이동평균선의 교차나 여러 지표의 조건을 함께 평가하려면, 지표마다 다른 출력값과 단위를 구분해야 했습니다.지표의 출력값과 비교 대상을 규칙으로 만들어 AND나 OR로 조합했습니다. 공용 지표 계산을 재사용하고, 단위가 다른 지표끼리는 비교를 막았습니다.CCI와 RSI 조건을 하나로 묶은 전략도 과거 시세에서 수익률과 체결 내역을 확인할 수 있게 했습니다.
AI 전략 어시스턴트사용자가 말로 설명한 매매 조건을 전략 초안으로 바꿉니다.AI가 지원하지 않는 지표나 연산자를 만들 수 있어, 생성된 조건을 전략에 쓸 수 있는지 확인해야 했습니다.기존 전략과 같은 규칙 검사로 지표와 연산자를 검증했습니다. 검증을 통과한 초안만 보여 주고, 사용자가 선택한 경우에 전략을 저장했습니다.지원하지 않는 조건을 거부하고, 초안 생성만으로 전략이 저장되지 않는 것을 시험으로 확인했습니다.
